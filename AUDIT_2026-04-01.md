## Executive Summary

The libraries workspace has materially improved since the March 30 snapshot. The original P0 (governance gate fail-open) is properly closed. The connection pool, HNSW sidecar lifecycle, and CEA persistence layer are all hardened. The test suite is substantial (1,312 test functions) with good integration coverage through the OODA loop. Remaining issues are real but none are critical — they're the kind of problems that cause operational annoyance rather than data loss or silent corruption.

**Overall Score: 8.4 / 10** (up from 8.1)

## What Moved Since March 30

### Governance Gate — P0 CLOSED

The governance gate (`forge-pilot/src/governance_gate.rs`) is the most important fix in this snapshot. `GovernanceMode::Strict` returns `Err(GovernanceGateError::NoGovernanceClaims)` when no governance claims exist, and `Err(GovernanceGateError::ObservationFailed)` when observation fails. The `observe_governance_with_mode` API forces callers to make an explicit fail-open vs fail-closed choice. `gate_execution_with_mode` promotes `Blocked` results to errors in strict mode. 16 unit and integration tests cover both modes including empty-store, populated-store, active-incident-blocks, degradation handling, and serde roundtrip.

The `governance` feature is in `forge-pilot`'s default features (`default = ["governance"]`), so the gate compiles and runs in every standard build. The loop runner in `loop_runner.rs` correctly halts with `HaltReason::GovernanceIncidentHalt` or `GovernanceAuthorityInsufficient` when the gate blocks.

### Connection Pool — Hardened

The `SqlitePool` in `semantic-memory/src/pool.rs` now has RAII `ReaderGuard` that returns reader slots even on panic. The writer lock recovery path checks `is_autocommit()` and rolls back open transactions on poison recovery. A dedicated test (`writer_mutex_poison_recovery_rolls_back_open_txn`) verifies that a panicked write transaction is rolled back and subsequent writes succeed.

### HNSW Sidecar — Rebuild Path Complete

The HNSW lifecycle handles every failure mode: stale sidecar detection (SQLite count vs HNSW count comparison), pending-ops journal (`pending_index_ops` table), dirty-sidecar flag, panic-safe save via `catch_unwind`, and full rebuild-from-SQLite through `recover_hnsw_sidecar_sync`. The `MemoryStore::open` path has explicit recovery branches for embeddings-dirty, pending-ops-exist, sidecar-stale, sidecar-missing, and orphan-embeddings scenarios.

### CEA Persistence — Transaction-Safe

`update_graph_with_tx` accepts caller-provided transaction handles, avoiding nested transactions. The `cea_edges` table schema carries `alpha` and `beta` columns confirming Beta-distribution priors persist across restarts.

### Workspace Lints — Enforced

`unsafe_code = "deny"`, `clippy::todo = "deny"`, `clippy::dbg_macro = "deny"`, `clippy::unimplemented = "deny"`, `clippy::expect_used = "warn"` at workspace level. Zero TODO/FIXME/HACK markers found in production code.

## Findings

### Finding 1: `unreachable!()` in Production Code Paths

**Severity:** HIGH  
**Location:** `forge-pilot/src/act.rs:323`, `forge-pilot/src/main_support/mod.rs:420`, `knowledge-runtime/src/obs/trace.rs:388`

**Problem:** `unreachable!()` panics unconditionally. In `act.rs:323`, it sits at the bottom of `execute_oracle_plan`'s match on `PlanKind`. The match covers all oracle variants and falls through to `unreachable!()` for non-oracle variants. This is logically correct today because the caller (`execute_plan`) dispatches non-oracle plans separately. But the `unreachable!()` creates a hard crash path that will fire if `PlanKind::LlmGenerated` (explicitly planned per the roadmap) is added to the oracle match arm by mistake.

In `main_support/mod.rs:420`, `unreachable!("provider presence checked")` assumes a provider was validated upstream. If the validation logic changes, this panics with a message that provides no actionable context.

**Impact:** Adding `PlanKind::LlmGenerated` (on the roadmap) will crash the loop runner if the dispatch logic isn't updated in lockstep.

**Fix:** Replace all three with proper error returns:
```rust
// act.rs
_ => return Err(PilotError::Other(format!(
    "unsupported plan kind for oracle execution: {:?}", plan
)))
```

### Finding 2: No HTTP Timeout on `reqwest::Client::new()` in main_support

**Severity:** HIGH  
**Location:** `forge-pilot/src/main_support/mod.rs:505`, `forge-pilot/src/main_support/mod.rs:546`

**Problem:** Both Ollama and OpenAI chat clients use `reqwest::Client::new()` with no timeout. The `OllamaEmbedder` in `semantic-memory/src/embedder.rs:55` correctly uses `Client::builder().timeout(Duration::from_secs(config.timeout_secs))`, so the pattern exists in the codebase but wasn't applied to the TUI chat paths.

If Ollama hangs during model loading or under VRAM pressure on the GTX 1070, the TUI thread blocks indefinitely. The user has to kill the process.

**Impact:** Hung TUI during LLM inference. On constrained hardware this is not a rare edge case.

**Fix:**
```rust
let client = reqwest::Client::builder()
    .timeout(Duration::from_secs(300))
    .build()
    .map_err(|e| format!("failed to build HTTP client: {e}"))?;
```

### Finding 3: `main_support/mod.rs` is a 1,591-Line Monolith

**Severity:** MEDIUM  
**Location:** `forge-pilot/src/main_support/mod.rs` — 32 functions, 7 responsibilities

**Problem:** This file contains CLI argument parsing, TUI interactive loop, LLM provider chat functions (Ollama + OpenAI), SSE/JSON streaming parsers, observation/candidate/report formatting, resource opening/path detection, and loop status management. It is the single largest concentration of unrelated responsibilities in the workspace.

**Impact:** Any change to the TUI risks breaking CLI behavior. The file exceeds practical review granularity. A diff that touches 3 functions could silently break 5 others. This was flagged in prior audits and remains unchanged.

**Fix:** Split into `cli.rs`, `tui.rs`, `provider.rs`, `explain.rs`, `storage.rs`. The function list already clusters naturally around these boundaries.

### Finding 4: Unbounded `PilotHistory` Growth in Daemon Mode

**Severity:** MEDIUM  
**Location:** `forge-pilot/src/history.rs`

**Problem:** `PilotHistory.entries` is a `BTreeMap<String, TargetHistoryEntry>` with no cap. Each entry accumulates `prior_attempt_bundle_ids: Vec<String>` and `prior_outcomes: Vec<String>` without bound. In the TUI's `start_closed_loop` daemon mode, the runner executes indefinitely.

**Impact:** Memory grows monotonically proportional to `O(unique_targets × attempts_per_target)`. On a laptop sharing RAM with Ollama, this eventually contributes to memory pressure in long sessions.

**Fix:** Cap `prior_attempt_bundle_ids` and `prior_outcomes` to the most recent 20 entries (or configurable). The exhaustion check only needs the last outcome, not the full history.

### Finding 5: `DefaultHasher` Used for Deterministic Digest

**Severity:** LOW  
**Location:** `forge-pilot/src/orient.rs:166-177`

**Problem:** `bounded_region_digest` uses `std::collections::hash_map::DefaultHasher`. Rust explicitly documents that `DefaultHasher` is not guaranteed stable across versions or platforms. The digest flows into `TargetNormalization` which is serialized into loop reports and verification cases.

**Impact:** Upgrading the Rust toolchain could change region digests for identical observations, breaking cross-version comparison of loop reports.

**Fix:** Replace with `blake3::hash` (already a workspace dependency) for a stable, portable digest.

### Finding 6: Missing NaN/Infinity Validation on HNSW Insert

**Severity:** LOW  
**Location:** `semantic-memory/src/hnsw.rs` — `insert_with_id` and `validate_dimensions`

**Problem:** `validate_dimensions` checks vector length but not element validity. A vector containing NaN or infinity values will be inserted and produce NaN distances for all subsequent searches against it, silently degrading every query result.

**Impact:** A single corrupted embedding from a malformed Ollama response degrades all vector search without any visible error.

**Fix:** Add to `validate_dimensions`:
```rust
if vector.iter().any(|v| !v.is_finite()) {
    return Err(MemoryError::HnswError(
        "embedding contains NaN or infinity values".into()
    ));
}
```

### Finding 7: `profile-runtime` Composition Logic Has Thin Test Coverage

**Severity:** LOW  
**Location:** `profile-runtime/src/compose.rs` (982 lines, 26 functions) vs `profile-runtime/tests/` (364 lines, 13 tests)

**Problem:** The composition engine implements 7 fold classes (`Union`, `Intersection`, `MinOfMaxima`, `MaxOfMinima`, `EarliestExpiry`, `ConflictIfDifferent`, `BlockDominant`) with exception handling, conflict detection, and block entry generation. The test suite covers basic roundtrip and fixture conformance but doesn't exercise adversarial composition scenarios — e.g., conflicting contributions from multiple profiles in the same obligation family, or exception classes that partially match blocking contributions.

**Impact:** Composition bugs would produce incorrect constitutional obligation sets, which gate execution decisions downstream.

**Fix:** Add property-based tests (proptest is already a workspace dependency) for composition with random obligation contribution sets, verifying fold class invariants (e.g., intersection ⊆ every input, union ⊇ every input, min ≤ every input's max, etc.).

## Architecture Assessment

### Strongest Aspects

**The verification control-plane ledger is genuinely novel.** The flow from `VerificationCase` → `CheckPlan` → `VerificationAttempt` → `ControlReceipt` → `LedgerEntry` → `adjudicate_case` → `replay_case` is a complete event-sourced verification ledger where every execution decision is recorded as an immutable event and can be replayed to reconstruct terminal state. The `replay_case` function in `verification-control` accepts a ledger entry slice and deterministically produces the final case disposition. I'm not aware of any open-source Rust agent framework that implements this pattern. It's the kind of infrastructure that makes the system auditable in a way that log-based approaches can't match.

**The OODA loop orchestration is thorough.** `loop_runner.rs` is 1,073 lines of dense orchestration, but every iteration correctly threads governance observation → target extraction → scoring → candidate selection → policy evaluation → permit issuance → execution → calibration → adjudication → rollback → receipt generation. The `LoopIterationReport` captures 27 distinct artifact slots. This is not over-engineered — each slot corresponds to a real decision point that an operator needs to inspect when debugging verification behavior.

**The connection pool is production-grade.** Single-writer + N-reader with WAL mode, bounded wait with condvar timeout, RAII guards for reader slots, and poison recovery with transaction rollback. The `writer_mutex_poison_recovery_rolls_back_open_txn` test is especially good — it simulates a panic mid-transaction and verifies that the speculative writes don't persist and that the connection remains usable after recovery.

**The CEA attribution pipeline is well-calibrated.** Softmax-normalized candidate scoring with configurable temperature, Blake3-based deterministic run hashing, proportional multi-cause weight assignment with distance decay, and proper weight bucketing (nano-scale quantization) for canonical ordering. The `AttributionConfig::validate()` method catches every degenerate configuration.

**Test infrastructure quality is high.** The `forge-pilot/tests/common/mod.rs` provides a complete test harness that constructs evidence bundles, persists them in ForgeStore, exports through the canonical V3 envelope path, imports into MemoryStore, and verifies round-trip fidelity. This is integration testing at the right abstraction level.

### Biggest Risks

1. **The `main_support` monolith** — At 1,591 lines spanning 7 responsibilities, this is where regressions will hide and where contributor friction will be highest.

2. **The `unreachable!()` calls** — These are specifically dangerous because `PlanKind::LlmGenerated` is on the near-term roadmap. A new contributor adding that variant will hit a crash that looks like a Rust bug rather than a missing match arm.

3. **Profile composition test gap** — The composition engine gates execution decisions through obligation folding. The 7 fold classes are complex enough that edge cases (partial exception matches, mixed numeric/string values, blocking contributions with admissible exceptions) need property-based testing.

### Comparison to Industry Equivalents

The verification control-plane (ledger-replay, typed receipts, adjudication) is ahead of anything in the open-source Rust agent ecosystem. LangGraph, CrewAI, and AutoGen don't have verification ledgers — they log execution traces but don't provide deterministic replay or formal adjudication. The closest analog is Temporal's workflow replay, but that's a general-purpose workflow engine, not a verification-specific system.

The HNSW + SQLite + FTS5 hybrid search with RRF fusion in `semantic-memory` is comparable to what ChromaDB or LanceDB offer, but with the critical addition of the durable pending-ops journal and authoritative-SQLite recovery path. Most vector stores treat the index as authoritative; making SQLite authoritative and the HNSW a recoverable sidecar is the right local-first design.

The CEA attribution system has no direct open-source equivalent. The closest thing conceptually is Weights & Biases experiment tracking, but CEA attributes causal effects to specific edit operations at line-level granularity with proportional multi-cause assignment, which is a different (and harder) problem than experiment-level metric tracking.
