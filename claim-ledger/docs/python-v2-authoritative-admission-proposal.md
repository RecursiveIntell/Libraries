# Proposal: opt-in Rust-owned admission of fresh Python ClaimLedger V2 support

**Status:** design proposal, not an implemented API, admission, migration, release, or permission to activate. Source cutoff: Libraries draft #41 `8a0fce9a09a88ab987f01db3d78d8635f91988db` (`claim-ledger` staged at unreleased `0.3.0`); Python ClaimLedger draft #18 `6c919ca97181a90e7ce14554ab03b16b84f984fe`. The operator selected an opt-in authoritative Rust admission target. The choice does not validate a particular issuer, proof, ID mapping, or storage transaction.

## Existing boundaries and P0 precondition

- `LedgerEvent::SourceSupportObservationV1` records source-reported refs and is **not** support. `SnapshotProjection::event_is_projectable` excludes both that event and `SupportAdmission`; compaction retains them or fails closed (`claim-ledger/src/ledger.rs`).
- `claim-ledger-mcp/src/server.rs` currently interprets a `SupportAdmission` event as queryable support in `claim_rows` (lines 38–55), while snapshot V1 does not fold it. `claim_ledger_query` calls `claim_rows` after loading the file **without** a head-verification step; the separate status/verify handlers derive an expected head from that same file, not from an independent trust anchor. **Do not expose an authoritative import while this query/projection discrepancy exists.** Phase A must disable or explicitly qualify *all* legacy `SupportAdmission`-derived query support until a separately defined verification mechanism proves it; merely gating new imports is insufficient. Test with a well-hashed forged-admission event and an independently trusted expected-head source. Do not make an unverified event projectable to rescue the query.
- `ArtifactEnvelopeV1::verify` binds exact artifact bytes to a domain-separated digest and checks Ed25519 signature, verifier-context signer key, authorized signer, time window, and admitted policy. It neither parses V2 nor proves support. A producer-declared key or `policy_admission.admitted` is not a trust root.
- **Separate Python-source evidence, not independently certified by this Rust owner:** the candidate `ClaimLedger/claim_ledger/{admit/support.py,admit/transaction_prepare.py,admit/preparation_store.py,core/bundle.py}` and `docs/release/CLAIM_BUNDLE_V2_BOUNDARY.md` describe retained V2 predecessors, an unkeyed partial `history_digest`, proposal-only exact-byte storage, and refusal of V2 ledger-backed admission. `tests/fixtures/legacy_v1_pr2_admitted_bundle.json` and `tests/test_bundle_v2_history.py` witness a V1 missing predecessor that cannot be promoted; draft ClaimLedger #18 `6c919ca97181a90e7ce14554ab03b16b84f984fe` hosts a fresh two-admission negative mapping test. Those are candidate source/test results at the cited Python head, **not** Rust admission or independent external provenance. Bind and rerun the exact Python artifact and schema before Phase B; never reconstruct a V1 predecessor from IDs.
- A future implementation would place event/admission semantics and deterministic verification in the Rust library, subject to the unresolved proof/permit and issuer decisions below. The present library provides deterministic ledger/event values and verification but does not make trust decisions. Per `claim-ledger/README.md`, the MCP/store composition owns durable I/O, concurrency, and crash recovery. **The trusted signer/permit issuers, key rotation/revocation, trusted time and independent head authority are not assigned by that README or this proposal**; Phase B/D must name and verify their owners before any admission implementation. Python owns extraction and its V1/V2 workflow; its IDs remain scoped source references. Forge causal-verification evidence is a different family.

## Goal and forbidden scope

Design a *new versioned* Rust-native admission lane for an exact, fresh V2 artifact after two independent gates: trusted source provenance and a Rust-side proof/permit decision. One committed Rust ledger event is the admitted-support authority; any snapshot, MCP query, source-reference mapping, or output bundle is a rebuildable projection of that event. It must be possible to abstain without a write.

Do **not** route this through existing `SupportAdmission` or `SourceSupportObservationV1` as if either were verified admission; reinterpret V1, invent missing predecessors, silently translate Python IDs into Rust IDs, rely on a JSON `verified` flag, persist an independent alias registry, or treat a signed source artifact as proof that its reported support state is correct. No current crate version, CI result, or proposal text grants live authority.

## Proposed admission boundary, not yet implemented

1. **Exact input and identity.** The request supplies bounded original UTF-8 V2 bytes, explicit `ClaimLedgerBundleV2` schema, source artifact byte SHA-256, source bundle ID, claim/admission/predecessor/successor refs, intended Rust scope, method, and an idempotency key. Keep raw byte identity even if a parser creates a view. A strict ingress rejects duplicate keys at any nesting depth, unknown fields, coercion, non-finite numbers, unsupported versions, oversized inputs, absent predecessor, mismatched ownership/claim pointer, borrowed supersession edges, and changed source/evidence/proof fields. A Rust-owned reference interpreter must independently validate the V2 subset it admits; merely trusting Python `validate_bundle` or a source `history_digest` is insufficient. The accepted subset and cross-language canonical-byte rules require their own versioned specification and fixtures.
2. **Source trust gate.** A verifier-owned `EnvelopeVerificationContext` must verify an envelope over the **same original bytes** under configured signer keys, authorized signer ID, trusted-time bounds, and a named admitted source policy. Check revocation/rotation and the raw-byte SHA separately; the envelope's own domain-separated digest is not the raw SHA. Unsigned, unknown signer, stale/revoked policy, wrong bytes, or absent trust configuration fail without an admitted event. A test key is fixture-only, never a production default. **Open owner decision:** no durable signer-key registry, rotation/revocation procedure, or trusted-time issuer is selected by this proposal; the present context type does not supply those capabilities.
3. **Support decision gate.** Independently validate the method-specific **proof bytes**, their claim/source-span/evidence/transition binding, proof-debt consequences, and a scoped operator/control permit (issuer, scope, policy version, expiry, revocation and one-shot/replay semantics). Presence of a digest, source-reported `supported`, source waiver, or `EnvelopeVerificationStatus::FullyVerified` is not this decision. **Open owner decision:** the permit issuer, verifier, first production proof profile and key/policy lifecycle remain unassigned. Until selected and tested, this gate returns `blocked`, not `supported`. `test_fixture_admitted` may exercise only a disposable fixture policy; it is not a production shortcut.
4. **Native identity and commit.** Only after both gates pass, construct a versioned admission intent and Rust-native claim/judgment/receipt IDs that bind the exact source artifact, scoped source refs, predecessor native identity, distinct transition identity, verified proof/permit digests, and policy version. The current claim+state-only helper is forbidden for this mapping. Detect collisions and source-ref conflicts; retain the Python refs as opaque, explicitly typed lineage fields in the canonical event. Do not mint a durable mapping for a rejected request. Define a language-independent, domain-separated preimage and literal known-answer vectors before an ID implementation.
5. **One truth owner.** Introduce a distinct versioned native admission event and a versioned snapshot fold. The event must carry sufficient verified references, decision, and identity to replay without retrieving a mutable Python bundle. `claim-ledger` validates/constructs it; a **not-yet-selected durable store/head owner** in the MCP composition must supply an atomic compare-and-append transaction and independent expected-head authority. The current pure library does not implement that storage fence. Source-to-native mapping and receipt are derived from the committed event, never independently mutable. V1 snapshot remains V1; unrecognized new events retain/fail closed, never silently become current support.
6. **Time and receipt.** Record source-asserted valid time, source recorded time, Rust verification time, permit decision time, and native ledger commit time as distinct fields. **Open representation decision:** define the clock authorities, UTC encoding/precision, and what happens if permit expiry or policy revocation occurs between verification and commit; a future durable store contract must require revalidation inside its final transaction fence. No current store capability is implied. The admission receipt binds exact source SHA, envelope verification result and trust-policy version, proof/permit decision and issuer/version, source and Rust refs, idempotency key, prior and committed ledger heads, event digest, projection generation, and degradation/abstention. A receipt cannot say success before the canonical event is durable and read back. A waiver is authorization to carry debt, not evidence or repayment.

## Crash, retry, and negative witness matrix

| Boundary | Required result |
|---|---|
| Parse, schema, source trust, proof or permit rejects | No native admission event, native ID mapping, or support projection; typed reason and optional non-authoritative diagnostic only. |
| Verified proposal before append | No success/admission. Exact retained input may be retried only after rechecking permit, policy, and expected head. |
| Concurrent exact requests | One committed event/receipt under the durable owner's transaction fence; all exact retries return that receipt. |
| Same key with changed bytes, scope, proof, policy or predecessor | Explicit conflict; no overwrite or second admission. |
| Append uncertain or response lost | Read an **externally authenticated** expected head and operation identity. Return original receipt if committed; otherwise retry only with verified original bytes and current permit. Quarantine if commit status cannot be determined. |
| Commit succeeds, projection or response fails | Ledger remains canonical. Read returns stale/unavailable until deterministic replay rebuilds and verifies the projection; never manufacture a success from a cache. |
| Rebuild, compaction or unknown event version | Rebuild current state from verified ledger and matching versioned fold, or fail closed/retain tail. V1 reader must not reinterpret V2 admission. |

Test a fresh exact V2 fixture through source and Rust validators, then negative fixtures for duplicate/unknown JSON fields, rehashed source/span/proof tampering, stale predecessor, same-state distinct judgments, colliding IDs, wrong signer/policy/time, forged producer-declared key, forged/expired/revoked permit, exact duplicate versus changed-key retry, conflicting concurrent requests, append fsync/commit uncertainty, crash before/after append, projection rebuild with source unavailable, and mismatched external expected head. An internally consistent digest or fixture signature alone is not proof of admission.

## Phases and acceptance gates

- **A — Resolve the P0 query mismatch.** Independently test `claim-ledger-mcp` query and canonical snapshot on the same event chain. Disable or explicitly label *all legacy* `SupportAdmission`-derived query support nonauthoritative until an independently verified transition path exists; do not only fence future imports. Name the durable store/head authority and verify its external expected-head source. No new admission API yet.
- **B — Freeze the byte/proof contract.** Pin exact Python V2 schema and source fixture, define the Rust accepted subset, signer/permit owners, proof profiles and known-answer ID/event preimages. Run cross-language negative corpus. If a proof method or issuer cannot be named, stop at `blocked`.
- **C — Implement verification-only Rust API.** No write, native ID allocation, or support projection; test strict parsing, source trust and method-specific proof separately. Keep observation-only behavior unchanged.
- **D — Native admission and durable composition.** Versioned owner event/snapshot fold plus store-owned atomic append/idempotency/recovery. Test each crash boundary under a disposable store and independently read back the exact committed head.
- **E — Consumer and release conformance.** Test MCP query, snapshot, compaction, source-to-native mapping, exact replay, legacy V1 refusal, clean-package and downstream consumers. Obtain a fresh public-claim review. Merge, release, trusted-key provisioning, and activation remain separate operator gates.

**Rollback/quarantine:** This proposal changes no writer or persisted state. Close/revert the proposal draft without migration. Future implementation must leave existing observation-only records and V1 readers intact; on uncertain append or trust failure, quarantine the operation and preserve exact source bytes and receipts for operator inspection rather than deleting or guessing history.
