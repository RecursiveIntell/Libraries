# Master Issue Matrix — Codex V5

**Source snapshot:** `new4.zip`  
**Method:** full tree inventory + deep static inspection of core architecture crates + lighter static inspection of peripheral crates/tests/vendor paths.  
**Execution target:** Codex handoff for a **safe architecture-closure pass**, not a speculative redesign.  
**Important caveat:** this is **static inspection only**. No successful full-workspace build/test run was executed in this environment.

## How to read this matrix

- **Phase ok now?** = acceptable to exist temporarily during migration.
- **V5 conformant now?** = whether the current state appears aligned with the canonical target-state law.
- **Mandatory next pass?** = whether Codex should treat the row as part of the next safe closure pass.
- **Fossil risk** = how likely this is to become the real architecture by inertia if left alone.
- **Proof** = `confirmed-static`, `inferred-static`, or `audit-gap`.

## Most important truth

This snapshot is **strong**, but it is still held back by:
1. unfinished `knowledge-runtime` execution semantics,
2. provenance/version law that is stricter than before but still semantically leaky at the memory boundary,
3. one real retry/trial bug cluster in `agent-graph`,
4. best-effort canonical lineage persistence in `job-queue`,
5. compat surfaces that can fossilize if left alone.

## Safe-pass bias for Codex

Codex should prefer:
- **deletion / demotion / stricter validation** over adding new public surface,
- **smaller behavioral tests** over more doctrinal commentary,
- **fencing legacy behavior harder** over inventing a third migration layer,
- **preserving dependency direction** over locally “cleaner” but architecturally wrong couplings.
