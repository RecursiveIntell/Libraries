# Hostile Audit — Claude 10-Angle Analysis

## Scope and method

This audit is grounded in static inspection of `libraries-source-clean-20260330.zip`, extracted and examined programmatically in a Linux container. No Rust toolchain was available for compilation, but all source files were readable and all scripts were inspectable. The audit is **code-grounded and evidence-cited** with exact file paths and line numbers.

## Top-line verdict

The libraries are **architecturally excellent** and **operationally drifted**.

The code quality is the highest I've seen in a solo-developer Rust codebase of this scale. Zero production `unwrap()`, zero `unsafe` in workspace members, zero `todo!()`, typed IDs everywhere, thiserror error types with descriptive payloads, and a real OODA loop that chains 10+ crates per iteration. The governance observation pipeline (GOV-001/GOV-002 from V28) is now fully wired with integration tests.

The remaining problems are all meta-layer: the repo tells four different stories about what date it represents, 78 root-level control documents create archaeological confusion, gate scripts have drifted from the code, and 56 enums have an undocumented wire-format decision.

## Ten-angle hostile audit

### 1. Wire-format integrity auditor

**Verdict:** 56 serializable enums lack `#[serde(rename_all = "snake_case")]`.

This isn't a style issue — it's a wire-format decision. These enums serialize variant names in PascalCase. If any data is ever persisted (which it will be for CLARA), adding `rename_all` later breaks deserialization.

Affected crates: forge-pilot (3 enums), knowledge-runtime (6), semantic-memory (2), semantic-memory-forge (4), living-memory (19), verification-adjudication (4), verification-control (2), verification-policy (4), attestation-exchange (9), continuity-runtime (1), remote-oracle-admission (2).

The fix is safe NOW because no production data has been persisted. After CLARA submission, this becomes a migration problem.

### 2. Error-handling sadist

**Verdict:** production error handling is strong with one systematic gap.

The good: `thiserror` everywhere, descriptive error variants with context payloads (e.g., `DimensionMismatch { expected, actual }`), proper `#[from]` conversions, a `ForgeError` type with 25 variants and a `.kind()` discriminant method.

The gap: 25 `.ok()` calls in `semantic-memory` production code silently discard Results. Most are defensible — quantization is optional, feature-gated dead code uses `let _ =`. But ~8 calls in `db.rs`, `episodes.rs`, `knowledge.rs` discard SQLite operation results. A failed SQLite write that returns `Ok(())` is a silent data loss vector.

### 3. Governance observation completeness reviewer

**Verdict:** the governance pipeline works but observes a narrow window.

`governance_gate.rs` observes 6 predicates: effect_preflight, assurance_ready, authority_delegation_valid, continuity_incident_active, constitutional_amendment_pending, mechanism_fit. This covers the decision-relevant surfaces.

But the governance crates define much more: attestation-exchange has 7 pub types, mechanism-runtime has 9, assurance-runtime has its own type surface. None of these are individually observable through the pipeline. The observation is "is assurance ready? yes/no" rather than "what does the assurance case look like?"

For CLARA V1, this is sufficient. The pipeline is wired, tested, and fail-open. But the observation window should be documented.

### 4. Convention enforcement auditor

**Verdict:** BTreeMap convention holds at 62% but is eroding.

55 BTreeMap references vs 36 HashMap references in all code. In production-only code: 33 HashMap references. The HNSW index HashMap usage is architecturally justified. The HashMap usage in `knowledge-runtime/entity/registry.rs` and `discovery-portfolio` is not.

### 5. Documentation coverage analyst

**Verdict:** doc comment coverage ranges from 14% to 73%, averaging ~45%.

Worst: forge-memory-bridge (14%), effect-runtime (34%), forge-pilot (38%), living-memory (40%). Best: stack-ids (73%), profile-runtime (66%), knowledge-runtime (56%).

Module-level `//!` docs are generally good where they exist — `governance_gate.rs` has excellent design-constraint docs. But most pub types lack `///` comments. `cargo doc` output will show a wall of undocumented types.

### 6. Gate/script integrity tester

**Verdict:** gate scripts have drifted from the code in at least two places.

`check_commit_permit_paths.py` expects `ExecutionPermit` in `llm-tool-runtime` but the actual type is `ToolExecutionPermit`. This gate will fail on current code.

`check_hotspot_budgets.sh` checks `main_support/mod.rs` at two different limits (1900 and 1600 via documented-exception). This creates a confusing failure mode.

12 stale versioned scripts (check_v9 through run_v16_v20) remain in the active scripts/ directory.

### 7. Hotspot concentration analyst

**Verdict:** 22 files exceed 800 production lines.

Top 5: `profile-runtime/adapters.rs` (1791), `living-memory/lab/evidence.rs` (1617), `semantic-memory/db.rs` (1608), `semantic-memory/lib.rs` (1593), `forge-pilot/main_support/mod.rs` (1588).

The GPT audit correctly identifies this as a growing risk. However, these files are not monolithic blobs — they're densely typed with many small structs. The real maintenance risk is in `loop_runner.rs` (1062 lines of control flow) and `runtime/core.rs` (1209 lines).

### 8. Trust-chain completeness reviewer

**Verdict:** `attestation-exchange` is a forward declaration with zero integration.

The crate exists as an optional dependency in forge-pilot. No code imports or references its types. `AttestationEnvelopeV1`, `TrustRootSetV1`, and `TransparencyReceiptV1` exist as complete typed artifacts but have no consumers.

This is not a bug — it's a scope boundary. But it should be explicitly documented as a future integration point.

### 9. Schema versioning auditor

**Verdict:** clean and consistent.

133 v1 schemas, 3 v2, 2 v3. The v2/v3 schemas are confined to `semantic-memory-forge` (ExportEnvelopeV3, ForgeToolReceiptV2) and `forge-memory-bridge` (ProjectionImportBatchV3). Schema registry uniqueness passes. No conflicting schema names.

The schema versioning is well-managed. No issues found.

### 10. DARPA submission readiness reviewer

**Verdict:** the code is credible; the repo packaging is not.

A DARPA reviewer opening this repo would see:
- A README titled "finish_pack_2026-03-24" that describes a remediation pack
- 78 root-level markdown and JSON files from multiple audit generations
- Multiple `CANONICAL_STACK_SPEC` versions
- 6 `target-*` build artifact directories
- Gate scripts that reference old pack versions

The code underneath is serious systems engineering. The packaging obscures that.

**What the reviewer needs to see:**
1. A project README that says what RecursiveIntell is
2. Build instructions that work
3. A clean root directory with a clear entry point
4. A passing gate lane
5. cargo doc output with >80% documented types

## Hostile conclusion

This stack is not failing. It is not even struggling. The architecture works, the types are disciplined, the governance pipeline is wired, and the test surface is real.

What's happening is simpler and more mundane: **the repo has accumulated audit artifacts faster than it has cleaned them up.** Every audit cycle added docs, scripts, matrices, playbooks, and status dashboards — but none were retired. The result is a repo that looks like it's in crisis when it's actually in good shape.

The fix is straightforward: archive everything that isn't current, unify the truth surface, fix the two broken gate scripts, add `rename_all` to 56 enums, and raise doc coverage. That's 6-10 hours of focused work with AI assist.

> The engine runs clean. The garage needs organizing.
