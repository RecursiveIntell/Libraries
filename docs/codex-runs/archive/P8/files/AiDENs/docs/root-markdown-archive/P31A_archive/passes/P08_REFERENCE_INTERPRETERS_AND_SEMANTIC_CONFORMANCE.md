# P08 — Reference interpreters and semantic conformance harness

## Phase

Contracted core

## Purpose

Add small independent interpreters that define expected semantics for plans, capabilities, receipts, permits, boundary repair, and later temporal queries.

## Why this pass exists

Specs become elegant fan fiction without a semantic oracle. The research repeatedly calls for reference interpreters and differential/conformance harnesses.

## Implementation steps

1. Create aidens-testkit reference modules for plan->exposure, provider route, permit, boundary repair, and receipt lineage.
2. Add golden fixtures in tests/fixtures/reference/*.json.
3. Compare production implementations against reference for each fixture.
4. Add property tests for exposure monotonicity: adding permissions may expose more tools; removing permissions cannot expose more.
5. Add regression conversion path for any discovered counterexample.

## Acceptance gates

- Reference fixtures cover all provider kinds, risk classes, memory modes, receipt levels, and tool lifecycle states.
- Any production/reference mismatch fails tests with human-readable diff.
- The testkit is dependency-light and does not call production internals in a circular way.

## Required tests

- Unit tests for all new artifact constructors and policy decisions.
- Integration tests covering the pass's primary CLI/runtime behavior.
- Golden fixture tests for any schema- or receipt-bearing artifact.
- Regression tests for every bug or counterexample found during the pass.

## Required command gate

```bash
cargo fmt --all --check
cargo check --workspace
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
bash scripts/verify.sh
```

If a command cannot run in the local environment, Codex must record the exact command and reason in the handoff packet.

## Forbidden shortcuts

- Do not make the reference interpreter a thin wrapper around production code.
- Do not bless implementation behavior by copying its bugs into fixtures.
