# P02 — Provider runtime truth and executable backend matrix

## Phase

Foundation / runtime

## Purpose

Make provider readiness and route labels reflect actual executable backends, not advertised theoretical capabilities.

## Why this pass exists

Current provider capability advertising can imply native tool-calling for providers whose executable boundary is not implemented. Provider truth is the root of honest tool exposure.

## Depends on

P01

## Primary crates / surfaces

- `aidens-provider-kit`
- `aidens-contracts`
- `aidens-cli`
- `aidens-runner`

## Artifact families introduced or hardened

- `ProviderBackendMatrixV1`
- `ProviderReadinessReceiptV1`
- `ProviderRouteReceiptV2`
- `ProviderCertificationFixtureV1`

## Implementation steps

1. Separate advertised capability from implemented capability: AdvertisedProviderCapabilityV1 vs ExecutableProviderCapabilityV1.
2. Add a backend matrix for disabled, mock, ollama, openai-compatible, openai, openrouter, anthropic.
3. Implement real OpenAI-compatible / OpenAI / OpenRouter / Anthropic HTTP boundaries or mark them unavailable without native route labels.
4. Route native_tool_loop=true only when a backend can actually send and receive tool calls in that provider dialect.
5. Add provider certification fixtures for each provider kind covering configured, missing key, missing model, network failure, malformed response, and tool-loop unavailable.

## Acceptance gates

- provider-check never reports native_tool_loop=true for an unavailable or unsupported backend.
- OpenAI/OpenRouter/Anthropic routes either execute real requests behind feature-gated clients or return provider-boundary-unavailable with native_tool_loop=false.
- Ollama route truth distinguishes ordinary chat from native tool loop if tool calling is not implemented.

## Forbidden shortcuts

- Do not use provider kind string alone to infer executable native capability.
- Do not label parser fallback as native.
