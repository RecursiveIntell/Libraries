# P03 — TurnExecutorV1, provider/tool loop, and budgeted dispatch

## Phase

Foundation / runtime

## Purpose

Replace one-shot provider completion with a budgeted turn executor that can expose tools, parse/receive tool calls, dispatch, and continue until final output or stop condition.

## Why this pass exists

Current runner is prompt -> provider.complete() -> text. Completion requires provider/tool/provider iteration with receipts and stop rules.

## Implementation steps

1. Define TurnExecutorV1 and TurnModeV1: no-tools, native-tool-loop, parser-fallback, provider-unavailable, budget-exhausted.
2. Extend provider request/response contracts to carry provider_tool_schemas and provider-specific tool call outputs.
3. Implement parser fallback using boundary compiler only as degraded path; it must never be reported as native.
4. Call ToolDispatcher from the runner and append canonical ToolReceipt plus ToolInvocationReportV1 to the run report chain.
5. Enforce max_tool_calls, max_retries, timeout/deadline, and no-recursive-tool-loop stop rules.

## Acceptance gates

- A mock/provider fixture can request repo-read and receive the tool result before final answer.
- Every tool call has a receipt linked to run_id, attempt_id, tool_id, input digest, output digest, and outcome.
- Budget exhaustion returns a degraded/blocked final state with receipt; it does not loop forever or silently truncate.
