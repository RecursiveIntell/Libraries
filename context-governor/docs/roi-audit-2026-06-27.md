# context-governor ROI audit — 2026-06-27

Scope: local crate inspection + verification + online ecosystem/paper sweep for highest-ROI improvements.

## Executive verdict

`context-governor` is already a useful seed crate: small, fast, publish-dry-run clean, and aimed at the right abstraction layer. The highest ROI is not learned/model compression yet. The highest ROI is to turn it from a fast receipt-bearing heuristic into a plugin-ready context engine with accurate token accounting, strict budget behavior, real semantic-memory persistence, and host adapters.

The direct Rust online comparison says the same thing: Ogham and Squeez are the closest public analogues. They are ahead on host integration, reversible stores, exact token counting, content-type compression, and strict budget cascades. `context-governor` is ahead/competitive on simple receipts and clean crate-agnostic minimalism, but it needs the missing operational glue.

## Local strengths

1. Correct abstraction boundary
   - It is crate-/agent-agnostic.
   - It does not pretend to extend hosted model KV cache.
   - It frames HyperQuant-style behavior as allocation/rate-distortion, not text codec magic.

2. Receipts are first-class
   - The output includes transcript hashes, allocation plan ID, fallback refs, warning list, approximate token counts, and loss-report container.

3. Exact fallback exists
   - Summarized/omitted/quarantined items are stored exactly and can be expanded by item ID.

4. Fast enough
   - Release benchmark says sub-40 ms even at 2,000 synthetic messages.

5. Dependency footprint is modest
   - No LLM runtime deps.
   - No duplicate cargo deps.
   - No unsafe in crate source found by grep.

6. Release gate is clean
   - fmt, clippy, tests, docs, dry-run all passed.

## Local weaknesses / gaps

1. `semantic_memory_enabled` is a placeholder
   - It exists in `CompactionPolicy`, but `semantic_memory_fact_ids` and `semantic_memory_document_ids` are always empty.
   - This is a shadow-truth risk: API implies integration that does not exist.

2. `allocator` is a metadata string, not a strategy
   - `CompactionPolicy.allocator` is copied into the plan, but no alternate allocator is dispatched.
   - No HyperQuant bridge or trait exists yet.

3. Token counting is crude
   - `approx_tokens_text` is char-count / 4.
   - This is fine for smoke tests, weak for real provider budgets.
   - Online ecosystem shows `tiktoken-rs` is mature and heavily used.

4. Budget handling is safety-first but incomplete
   - It warns when output exceeds target, but does not offer hard/soft budget modes.
   - This is acceptable for v0.1.0 but not enough for production context engines.

5. Summary/loss report is too shallow
   - `SummaryLossReportV1.evidence_lost` is always empty.
   - `preserved_claims`/`omitted_claims` are item IDs, not extracted claims.
   - Summary is previews, not structured task state.

6. Classifier is hardcoded substring logic
   - Good enough for seed, but fragile.
   - Examples: any `likely` quarantines content even if the source is quoting a user instruction or a verified paper title.
   - `contains_path_signal` matches broad extensions like `.md` anywhere in text.

7. No content-type-specific compression
   - Tool logs, JSON, diffs, code, prose, cargo output, and search results all get the same treatment.
   - This is where Squeez/Ogham-like systems are ahead.

8. File store is minimal
   - It can save/load/list receipts.
   - It has no content-addressed blob layout, index, retention, compaction, or query over all stored receipts.

9. CLI is one-shot only
   - No `compact`, `expand`, `search`, `diff`, `store`, `bench` subcommands.
   - Plugin authors would have to embed the library or implement wrappers themselves.

10. No real agent-task eval
   - Current benchmark proves speed/token reduction, not downstream quality.
   - There is no replay harness comparing answerability before/after compaction.

11. Packaging polish gaps
   - No checked-in `LICENSE` file despite `license = "Apache-2.0"`.
   - README has ASCII architecture but no SVG/diagram asset.
   - No changelog/release notes.

## Highest-ROI improvement plan

### P0 — Make the API honest and plugin-ready

1. Add exact token accounting behind feature flags
   - Add `tiktoken` feature using `tiktoken-rs`.
   - Keep char/4 as fallback with explicit `TokenEstimateKind` in receipt.
   - Why: current budgets are approximate; production context engines need provider-aware budgets.
   - Effort: 0.5-1 day.
   - ROI: very high.

2. Add strict/soft budget modes
   - Add `BudgetMode::{SoftWarn, HardCascade, FailClosed}`.
   - `SoftWarn`: current behavior.
   - `HardCascade`: keep protected items, summarize/receipt/drop lower priority until under budget.
   - `FailClosed`: return `BudgetExceeded` if exact-preserve items alone exceed budget.
   - Why: Ogham has this; current warning-only behavior is not enough for a real context engine.
   - Effort: 1 day.
   - ROI: very high.

3. Implement semantic-memory adapter surface or remove placeholder field
   - Option A: generic `MemorySink` trait with `archive_item`, `archive_receipt`, `search_archives`.
   - Option B: remove `semantic_memory_enabled` until actual integration lands.
   - Best: implement trait, then semantic-memory-mcp/Hermes adapter owns actual network/tool call.
   - Why: current API implies semantic-memory IDs but always returns empty lists.
   - Effort: 0.5-1.5 days.
   - ROI: very high.

4. Add CLI subcommands
   - `context-governor compact < request.json`
   - `context-governor store --dir DIR < response.json`
   - `context-governor expand --dir DIR --receipt ID --item ID`
   - `context-governor search --dir DIR --query TEXT`
   - `context-governor diff < response.json`
   - Why: lets any agent shell out immediately without linking Rust.
   - Effort: 1 day using `clap`.
   - ROI: very high.

### P1 — Catch up to direct Rust competitors where it matters

5. Add content-type classifiers and compressors
   - Types: logs, cargo output, stack traces, JSON, diffs, code, markdown/prose, search results.
   - Start deterministic:
     - logs: keep errors + command + last N lines + counts
     - JSON: key skeleton + selected fields + hash
     - diffs: file headers + changed hunks + stats
     - cargo output: package/result/errors/warnings summary
   - Why: Squeez and Ogham are ahead here; this is where token savings become reliable.
   - Effort: 2-4 days.
   - ROI: high.

6. Structured summary/loss report
   - Extract fields: active task, acceptance gates, files touched, commands run, failures, decisions, unresolved questions, exact fallback handles.
   - Populate `evidence_lost` and `high_risk_omissions` with meaningful data.
   - Why: current summary is preview lines; useful, but not enough to avoid stale-summary errors.
   - Effort: 1-2 days.
   - ROI: high.

7. Searchable store index
   - Keep `FileContextStore`, add optional in-memory/BM25 index over saved receipts/exact store.
   - Later semantic-memory can supersede it, but local plugin users need something now.
   - Why: exact fallback is only useful if agents can find which item to expand.
   - Effort: 1-2 days.
   - ROI: high.

8. Better classifier rules + explicit pinning
   - Add `Message.metadata` conventions for `pinned`, `must_preserve`, `sensitive`, `source`, `tool_name`, `command_exit_code`.
   - Make substring heuristics secondary to metadata.
   - Why: host adapters can provide stronger signals than string matching.
   - Effort: 1 day.
   - ROI: high.

The crate's highest-ROI path is operational:
- honest token budgets,
- strict budget modes,
- semantic-memory persistence,
- CLI/plugin subcommands,
