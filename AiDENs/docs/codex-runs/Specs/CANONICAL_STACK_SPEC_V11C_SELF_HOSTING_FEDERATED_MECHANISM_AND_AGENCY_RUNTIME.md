# Canonical Stack Spec v11C — Self-Hosting, Federated, Mechanism, and Agency Runtime

**Status:** Proposed v11C horizon target  
**Relationship to v11A:** v11A remains the constitutional artifact runtime core. v11C may not weaken artifact lifecycle, operator effects, proof economy, boundary compiler, or reference-conformance law.  
**Relationship to v11B:** v11B remains the regional recursive/subtractive runtime. v11C may not weaken right-graph, region, convergence, repair, causal, or lawful subtraction law.  
**Scope:** constitutional self-hosting, generated conformance, external artifact admission, federated settlement, mechanism/theory artifacts, agency preservation, and future governance hooks.

---

## 0. Purpose

v11C defines the **future-admission layer**.

v11A and v11B make the stack lawfully executable internally. v11C ensures the stack can safely grow into:

- self-described and generated spec artifacts;
- external artifact admission;
- cross-runtime federation;
- mechanism/theory search;
- user agency/influence governance;
- external attestations;
- future constitutional amendments.

v11C is not a demand that every horizon capability ship immediately. It is a requirement that v11+ not paint itself into an architectural corner.

The shortest definition:

> v11C reserves the lawful future: the stack can eventually compile its own constitution, admit external evidence, settle shared claims, represent mechanisms, and preserve user agency without creating shadow truth or self-authorizing automation.

---

## 1. Normative language

The words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

v11C distinguishes between:

- **reserved law** — artifact hooks and prohibitions that must be respected now;
- **activation law** — requirements that apply when the capability is enabled;
- **horizon law** — target behavior for later full implementation.

If a capability is not activated, its artifacts need not be fully implemented. However, existing implementation MUST NOT create incompatible substitutes that would break the reserved law.

---

## 2. Core thesis

Future stack power must be admitted through artifacts, not smuggled through tools, prompts, notebooks, external APIs, or generated files.

v11C therefore defines five horizon surfaces:

1. **constitutional self-hosting** — specs become artifacts that can be parsed, compiled, tested, simulated, challenged, and admitted;
2. **external admission/federation** — outside artifacts and remote runtimes are admitted through attestation, policy, equivalence, quarantine, and settlement;
3. **mechanism/theory runtime** — hypotheses, simulators, fit runs, invariance checks, and refuter suites become first-class artifacts;
4. **agency preservation** — influence, advice, memory-personalization, and consequential nudging become gateable and receipt-bearing;
5. **future-governance safety** — generated law never admits itself without human challenge/veto.

---

## 3. Constitutional self-hosting seed

### 3.1 Spec artifacts

Future spec law SHOULD become representable as canonical artifacts.

v11C reserves the following families:

- `SpecBundleV1`
- `NormativeASTV1`
- `SpecCompilerReceiptV1`
- `GeneratedSchemaBundleV1`
- `GeneratedReferenceInterpreterBundleV1`
- `GeneratedConformanceCorpusV1`
- `GeneratedMigrationPlanV1`
- `AmendmentSimulationV1`
- `SpecDriftReportV1`
- `HumanVetoReceiptV1`

### 3.2 `SpecBundleV1`

A spec bundle MUST include, once activated:

- spec id;
- spec version;
- relationship to prior law;
- normative sections;
- non-normative source basis;
- artifact families introduced/changed;
- compatibility claims;
- release-bar clauses;
- digest;
- signature/attestation refs if applicable.

### 3.3 `NormativeASTV1`

A normative AST MUST represent:

- obligations;
- prohibitions;
- permissions;
- artifact family references;
- precedence rules;
- activation conditions;
- release-bar gates;
- conformance surfaces;
- unresolved ambiguities.

### 3.4 Spec compiler

A spec compiler MAY generate:

- schemas;
- reference interpreter stubs;
- conformance fixtures;
- migration plans;
- proof-obligation sets;
- crate responsibility maps;
- issue matrices;
- release-gate checklists.

A generated artifact is not law until admitted through governance.

### 3.5 Human veto persists

No generated spec, schema, interpreter, conformance corpus, migration, or proof obligation may self-admit.

Human challenge/veto MUST remain possible for:

- new normative clauses;
- generated schemas;
- generated tests;
- proof-profile changes;
- authority-boundary changes;
- promotion-law changes;
- agency/influence policy changes;
- federation/admission changes.

### 3.6 Self-hosting safety rule

The stack MAY help draft its law. It MUST NOT become the final source of its law without human-governed admission.

Self-hosting is a conformance amplifier, not a coup. The paperwork gets a badge, not a throne.

## 4. External artifact admission

### 4.1 External artifacts are untrusted until admitted

Any artifact produced by another runtime, remote service, external API, model provider, connector, repository, user upload, or partner system is external until admitted.

External artifacts MUST NOT directly affect local truth-bearing state without admission.

### 4.2 Reserved families

v11C reserves:

- `AttestedArtifactEnvelopeV1`
- `AdmissionPolicyV1`
- `TrustRootV1`
- `ExternalArtifactQuarantineV1`
- `ExternalVerificationReceiptV1`
- `DisclosurePolicyV1`
- `CrossRuntimeEquivalenceBundleV1`
- `SharedReplaySliceV1`

### 4.3 `AttestedArtifactEnvelopeV1`

An attested external artifact MUST include:

- artifact ref/digest;
- issuer/runtime id;
- artifact family;
- schema version;
- attestation type;
- signing/verification material;
- trust-root ref;
- disclosure constraints;
- replay refs if any;
- proof/evidence refs if disclosed;
- admission state.

### 4.4 Admission policy

`AdmissionPolicyV1` MUST specify:

- admitted artifact families;
- required schema versions;
- trust roots;
- verification checks;
- disclosure requirements;
- quarantine defaults;
- allowed downstream uses;
- proof-profile requirements;
- equivalence requirements;
- expiry/revocation handling;
- dispute path.

### 4.5 Quarantine by default

If an external artifact lacks required schema, attestation, disclosure, digest, provenance, time coordinates, or verification, it MUST be rejected or quarantined. Silent partial admission is non-conforming.

## 5. Federated settlement seed

### 5.1 Local authority remains local

Federation MUST NOT create a new central truth plane.

A remote quorum, treaty, vote, or settlement MAY influence local decisions only through admitted artifacts and local governance law.

### 5.2 Reserved families

v11C reserves:

- `TreatyBundleV1`
- `SettlementCaseV1`
- `SharedDispositionV1`
- `FederatedDisputeBundleV1`
- `RemoteOracleReceiptV1`
- `CrossRuntimeEquivalenceBundleV1`
- `FederatedQuarantineV1`

### 5.3 Cross-runtime equivalence

Equivalence across runtimes MUST be explicit and challengeable.

`CrossRuntimeEquivalenceBundleV1` MUST distinguish at least:

- same episode;
- same claim lineage;
- same relation lineage;
- same execution attempt family;
- same intervention lineage;
- observational comparability;
- semantic compatibility only;
- unresolved equivalence;
- rejected equivalence.

A system MUST NOT collapse remote and local artifacts merely because they share text, embeddings, or approximate identifiers.

### 5.4 Settlement cases

A `SettlementCaseV1` MUST include:

- contested artifact/claim/relation;
- participating runtimes;
- treaty/admission basis;
- local evidence;
- remote evidence;
- disclosed proof profiles;
- equivalence bundles;
- dissenting views;
- proposed disposition;
- local acceptance/rejection;
- replay slices;
- dispute/challenge path.

### 5.5 Evidence quorum is not vote counting

Federated settlement MUST NOT rely on count-only agreement.

Agreement strength depends on:

- evidence independence;
- proof quality;
- disclosure completeness;
- trust roots;
- replayability;
- equivalence strength;
- known correlated failure modes;
- dissent and refutation state.

## 6. Mechanism and theory runtime seed

### 6.1 Mechanisms are artifacts, not notebooks

A mechanism/theory surface represents candidate explanatory structures:

- symbolic equations;
- causal structures;
- simulator families;
- graph mechanisms;
- sparse libraries;
- dynamical models;
- Hamiltonian/Lagrangian structures;
- Neural-ODE-like families;
- typed rule systems;
- learned structural hypotheses.

These MUST be artifactized before they influence risk-bearing action.

### 6.2 Reserved families

v11C reserves:

- `MechanismBundleV1`
- `TheoryVersionV1`
- `HypothesisLibraryV1`
- `SearchProgramV1`
- `SimulatorContractV1`
- `FitRunReceiptV1`
- `StabilityReportV1`
- `InvarianceReportV1`
- `ComparabilityReportV1`
- `TheoryRefuterSuiteV1`
- `MechanismPublicationReceiptV1`
- `TheorySupersessionRecordV1`

### 6.3 `MechanismBundleV1`

A mechanism bundle MUST include, when activated:

- mechanism id;
- representation family;
- structural assumptions;
- variables/entities;
- equations/rules/graph structure if applicable;
- simulator contract refs;
- fit run refs;
- evidence refs;
- known nuisance/confounder requirements;
- stability/invariance reports;
- refuter suite refs;
- publication status;
- supersession/dispute refs.

### 6.4 Observational equivalence warning

The runtime MUST distinguish:

- fits observed data;
- predicts held-out data;
- invariant under perturbation;
- identified under assumptions;
- causally identified;
- merely observationally equivalent.

A theory that fits well MUST NOT be treated as identified merely because it is elegant, compact, or high-scoring.

### 6.5 Simulator contracts

`SimulatorContractV1` MUST declare:

- inputs;
- outputs;
- state variables;
- stochasticity and seeds;
- environment requirements;
- invariants/conservation laws if any;
- numerical tolerances;
- replay requirements;
- validation fixtures;
- failure modes;
- budget/exactness class.

### 6.6 Refuter suites

A mechanism/theory SHOULD NOT be published for action-bearing use without `TheoryRefuterSuiteV1`.

Refuter suites SHOULD include, where relevant:

- negative controls;
- placebo checks;
- invariance tests;
- perturbation tests;
- stability checks;
- counterfactual checks;
- simulator consistency checks;
- out-of-distribution stress;
- alternative mechanism comparison.

## 7. Agency preservation layer

### 7.1 Governing principle

A stateful, memory-rich, tool-using assistant MUST NOT materially distort the user’s ability to make a free, informed, reversible decision by exploiting asymmetries of knowledge, time, trust, dependence, vulnerability, or attention.

This applies to Recall, AiDENs, coding agents, personal assistants, research agents, and any system that personalizes, repeats, nudges, persuades, advises, or acts.

### 7.2 Reserved families

v11C reserves:

- `InfluenceClassV1`
- `AdviceEnvelopeV1`
- `AgencyReceiptV1`
- `PersuasionBudgetV1`
- `VulnerabilityContextV1`
- `MemoryInfluenceTraceV1`
- `ConsentStateV1`
- `ReversibilityPlanV1`
- `AgencyIncidentRecordV1`

### 7.3 Influence classification

A user-facing output MUST be classified when it is:

- personalized from memory;
- repeated over time;
- emotionally supportive in a consequential context;
- likely to change offline behavior;
- related to health, finance, law, work, relationships, safety, identity, or major life decisions;
- a recommendation that could exploit user vulnerability or dependence;
- a request for the user to trust, rely, continue, purchase, consent, disclose, or delegate.

### 7.4 `InfluenceClassV1`

An influence class MUST include:

- output/action id;
- influence type;
- personalization basis;
- repetition count/context;
- urgency/framing markers;
- vulnerability context if known and lawful to use;
- reversibility;
- consequence tier;
- required disclosure;
- gating decision.

### 7.5 Advice envelope

`AdviceEnvelopeV1` MUST include, for consequential personalized advice:

- recommendation/action;
- evidence basis;
- uncertainty;
- alternatives;
- risks;
- reversibility;
- memory refs used;
- withheld/unknown context;
- user-agency safeguards;
- consent/approval if needed;
- escalation/refusal path.

### 7.6 Memory influence trace

If memory materially shaped advice, persuasion, or action, `MemoryInfluenceTraceV1` MUST disclose:

- memory artifacts used;
- memory artifacts withheld;
- personalization path;
- confidence/proof state of memory;
- whether the memory is current or stale;
- user-visible summary where appropriate.

### 7.7 Prohibited behavior

A conforming system MUST NOT:

- create false urgency;
- hide material uncertainty;
- manipulate dependency;
- personalize persuasion without disclosure where consequential;
- continue nudging after refusal unless safety policy requires limited follow-up;
- use private memory to exploit vulnerability;
- claim human-like care, loyalty, or exclusivity as a persuasive tactic;
- blur recommendation with completed action.

### 7.8 Agency receipts

When agency gates trigger, the system MUST emit `AgencyReceiptV1` containing:

- influence classification;
- gating result;
- disclosures shown;
- user consent/override;
- repetition/persuasion budget impact;
- action taken or refused;
- memory influence trace refs;
- incident/escalation if applicable.

## 8. Learned systems and future autonomy

### 8.1 Learned systems remain bounded

Learned models MAY assist:

- artifact ranking;
- proof-cost estimation;
- region selection;
- repair triage;
- subtraction candidate ranking;
- mechanism search;
- anomaly detection;
- abstention;
- agency-risk classification.

They MUST NOT:

- self-promote truth;
- rewrite schema law;
- erase proof debt;
- admit external artifacts;
- settle federation disputes;
- publish theories;
- waive agency gates;
- amend the constitution.

### 8.2 Training-label lineage

Any learned model used in a material role SHOULD have:

- training data lineage;
- label provenance;
- verified outcome refs;
- calibration report;
- drift report;
- failure taxonomy;
- allowed-use profile.

### 8.3 Autonomy escalation

Higher autonomy requires stronger receipts.

A system moving from advisory to action-taking MUST add:

- execution receipts;
- approval/permit receipts;
- rollback plan;
- agency/influence classification where user-facing;
- proof profile;
- audit surface.

## 9. Security, attestation, and transparency hooks

### 9.1 Evidence worth trusting needs integrity

v11C reserves support for:

- signatures;
- attestations;
- transparency logs;
- revocation status;
- trust roots;
- disclosure policies;
- tamper-evident receipt chains.

### 9.2 Tamper-evidence

Where artifacts support governance, compliance, high-trust federation, or external admission, they SHOULD be tamper-evident.

A tamper-evident receipt SHOULD include:

- content digest;
- signer/issuer;
- signing time;
- trust root;
- inclusion proof if transparency log used;
- revocation status;
- disclosure limits.

### 9.3 Redaction and disclosure

Redaction MUST NOT destroy proof semantics silently.

If proof-relevant content is redacted, the artifact MUST disclose:

- redaction class;
- proof impact;
- who may view original;
- whether verification remains possible;
- alternative verification if any.

## 10. v11C activation levels

| Level | Meaning |
|---|---|
| `reserved` | Artifact family names and compatibility hooks are reserved. Full implementation not required. |
| `schema_defined` | Canonical logical schema exists. |
| `receipt_emitting` | Runtime emits receipts but may not enforce full behavior. |
| `policy_enforced` | Governance/policy decisions enforce the artifact law. |
| `reference_checked` | Reference behavior/conformance fixtures exist. |
| `promotion_relevant` | Artifacts may affect promotion or authority only through lawful path. |
| `fully_activated` | Capability is production-active under release bar. |

Every v11C capability MUST declare activation level.

---

## 11. v11C release/horizon bar

A release may claim **v11C-reserved** compliance if:

1. It does not create incompatible artifact families for self-hosting, federation, mechanism search, or agency preservation.
2. It reserves or stubs the core artifact names in the artifact family index.
3. It prevents external artifacts from influencing local truth without admission.
4. It preserves human veto for spec/governance changes.
5. It prevents learned systems from amending law, waiving proof, or promoting truth.
6. It classifies at least high-risk user-facing personalized advice/action surfaces if those are enabled.
7. It distinguishes horizon artifacts from active authority.

A release may claim **v11C-active** compliance only if the relevant capability also has:

- canonical schemas;
- operator contracts;
- receipts;
- policy enforcement;
- reference fixtures or explicit temporary proof debt;
- governance challenge path;
- release-bar tests.

---

## 12. v11C non-goals

v11C does not require immediate full treaty runtime.

v11C does not require immediate full mechanism discovery.

v11C does not require the stack to self-amend.

v11C does not require global cryptographic transparency infrastructure for all artifacts.

v11C does not require every recommendation to emit heavy agency machinery; it requires classification and gating for consequential, personalized, repeated, or action-bearing influence.

---

## 13. Design warning

A future stack that admits remote artifacts without quarantine is not compliant.

A future stack that treats theory fit as truth is not compliant.

A future stack that lets generated law admit itself is not compliant.

A future stack that uses memory to manipulate the user while calling it personalization is not compliant.

A future stack that federates by count-only vote is not compliant.

v11C is how the system gets more powerful without becoming a very elaborate way to launder authority.
